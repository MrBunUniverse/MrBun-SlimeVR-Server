# Local SJ SlimeVR headset tracking capabilities

## Can Mac plus Quest 3S already provide an actual HMD pose to this app?

### Takeaway
The checked-out fork already implements a complete input route for head and wrist position and rotation from VRChat, through OSCQuery and OSC. This route is platform independent in server core and does not require SteamVR. This is source-level support, not a claim that the user's current running app is receiving packets.

### Cited Findings
- The handler subscribes to `/tracking/vrsystem/head/pose`, `/tracking/vrsystem/leftwrist/pose`, and `/tracking/vrsystem/rightwrist/pose`. On first head packet it creates `VRChat head`, assigns `TrackerPosition.HEAD`, declares both position and rotation, registers it, converts coordinates, sets status OK, and calls `dataTick`. — [VRCOSCHandler.kt:47](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VRCOSCHandler.kt:47), [creation and update:386](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VRCOSCHandler.kt:386).
- OSCQuery advertises a `SlimeVR-Server-*` service with `/tracking/vrsystem`, uses a selected local IP plus random HTTP port, and listens for `_osc._udp.local.` VRChat services named `VRChat-Client*`. Discovered services become OSC senders. No manual Scan button is needed to start this listener. — [VRCOSCQueryHandler.kt:15](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VRCOSCQueryHandler.kt:15), [startup:29](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VRCOSCQueryHandler.kt:29), [discovery:71](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VRCOSCQueryHandler.kt:71).
- OSCQuery initializes only when both VRChat OSC and OSCQuery are enabled; disabling OSC closes the packet receiver. — [VRCOSCHandler.kt:114](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VRCOSCHandler.kt:114), [receiver:276](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VRCOSCHandler.kt:276).
- The skeleton uses the selected head tracker's position and rotation directly for head transforms; if no head exists it can instead derive head rotation from neck or torso and use a null position when the localizer is disabled. — [HumanSkeleton.kt:778](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/tracking/processor/skeleton/HumanSkeleton.kt:778).
- A test source synthesizes a head packet and checks IP auto-detection. It does not prove headset networking or physical tracking, and was not run during this research. — [QuestAutoDetectionAndRpcTests.kt:55](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/test/java/dev/slimevr/unit/QuestAutoDetectionAndRpcTests.kt:55).

### Inferences
- For standalone Quest VRChat, the first thing to do is enable and observe the existing route, not add a new pose protocol. Actual supported head packets should create a tracker named `VRChat head`.
- mDNS discovery needs reachable LAN interfaces; network filtering, Wi-Fi client isolation, firewall rules, the selected local interface, and VRChat privacy settings remain live diagnostic concerns. These were not inspected.

### Gaps
- No current app process, saved settings, port listeners, network capture, headset firmware, live VRChat screen, or motion was inspected. No latency, packet rate, disconnect behavior, or physical calibration claim is verified.
- External VRChat documentation should verify that this endpoint is available in the current Quest release and describe its privacy switch and coordinate space. The following UI section records this fork's actual text, not an independently verified current VRChat screen.

## Which exact current UI controls enable the existing route?

### Takeaway
Use this fork's standalone mode and enable VRChat OSC plus OSCQuery. Selecting PC VR on this Mac is counterproductive for this route because that control disables VRChat OSC.

### Cited Findings

### Inferences
- User-facing sequence: start server; top bar connection status → turn on `Standalone mode (VRChat OSC)`; Settings → OSC → `VRChat OSC Trackers` → confirm both `Enable` and `Enable OSCQuery`; enable the two VRChat switches above; use the same reachable LAN; look for `VRChat head` and verify its actual movement.
- Confirm explicit server-side Enable even when the mode badge already says Standalone: the source default for the form is `enabled:false` and the mode preference is local storage.
- Body output toggles (`Chest`, `Hip`, `Knees`, `Feet`, `Elbows`) control sending computed trackers; they do not enable receipt of the head endpoint. Setting outbound address manually cannot fix blocked multicast discovery on its own.

### Gaps
- The deployed GUI may differ from the working tree, which has extensive pre-existing edits. No GUI screenshot or packaged build was inspected.
- No claim that the head privacy setting is already enabled on this Quest.

## What would require invention or extra development?

### Takeaway
The missing general feature is obtaining Quest pose outside an application that deliberately exports it, not accepting a head pose in SlimeVR. Existing server inputs can be reused for an experimental Quest sender, but each has details to validate. Native SteamVR is a separate runtime requirement that a new Mac bridge alone cannot provide.

### Cited Findings
- Desktop native SteamVR bridge creation has Windows named-pipe and Linux Unix-socket cases. The `else` case is empty, so macOS receives no native SteamVR driver or feeder bridge in this implementation. — [Main.kt:199](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/desktop/src/main/java/dev/slimevr/desktop/Main.kt:199).
- Server core always adds `WebSocketVRBridge` alongside platform bridges. The socket binds 21110. JSON `type:pos`, numeric `tracker_id:0`, `x,y,z,qw,qx,qy,qz` updates a registered `WebSocketHMD` with position and rotation. However the existing parser adds **0.2 metres to Y**, and its created tracker does not explicitly enable timeouts; a new sender must not be declared production-ready without resolving those assumptions. — [VRServer.kt:162](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/VRServer.kt:162), [WebsocketAPI.java:27](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/websocketapi/WebsocketAPI.java:27), [WebSocketVRBridge.kt:62](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/websocketapi/WebSocketVRBridge.kt:62), [parser:162](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/websocketapi/WebSocketVRBridge.kt:162).
- VMC accepts `/VMC/Ext/Hmd/Pos` with name, XYZ position and quaternion. This path currently supplies `trackerPosition:null`, creates an editable tracker, and enables timeout: automatic HEAD assignment is not provided merely because the address says Hmd. — [VMCHandler.kt:222](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VMCHandler.kt:222), [creation:281](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/osc/VMCHandler.kt:281).
- Slime UDP protocol has position packet 27; handler writes its position but does not call `dataTick`. Sensor creation declares rotation/acceleration, without `hasPosition:true`, so simply emitting packet 27 is not sufficient to assume a functional 6DoF HMD input. — [UDPPacket.kt:398](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/tracking/trackers/udp/UDPPacket.kt:398), [TrackersUDPServer.kt:168](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/tracking/trackers/udp/TrackersUDPServer.kt:168), [position handler:636](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/server/core/src/main/java/dev/slimevr/tracking/trackers/udp/TrackersUDPServer.kt:636).
- Existing Quest integration launches scrcpy display capture and audio capture. The reviewed capture argument builders request display video or audio, with no pose stream. A display mirror or connected ADB device is not evidence of pose ingress. — [quest-capture.ts:334](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/gui/electron/main/quest-capture.ts:334), [quest-audio.ts:388](/Users/sirjame/Documents/Project/SJ%20SlimeVR%20Sever%20Claude/gui/electron/main/quest-audio.ts:388).

### Inferences
- Minimal first experiment, if generic pose is desired: a Quest foreground OpenXR application reads its own real 6DoF head pose and sends an existing supported format to this Mac; inspect valid tracking, coordinate conversion, floor/recenter alignment, timestamp/packet age, and disconnect timeout. That is a plausible software project, not proof it runs alongside arbitrary Quest games.
- For VRChat-specific use, a coding model could improve discovery diagnostics, head packet freshness, and explicit HMD status in the GUI. Building a second pose pipeline before testing the existing one adds unnecessary work.
- Cross-application background head access and full PCVR on an M3 Mac require external platform/runtime evidence; local server code does not establish feasibility.
